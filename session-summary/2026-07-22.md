## 2. Current State — ✅ COMPLETED & VERIFIED (2 commits, pushed, tree clean)

**The diagnosis (why this mattered):** `refresh.yml` had **NO `push` trigger** —
only weekly cron + manual dispatch, and the ONLY Pages-deploy step was the tail of
that one big pipeline job. So a pushed `index.html` button change **did not deploy
at all** until the next weekly run or a manual dispatch — and *both re-download all
~750 MB + regenerate everything* just to ship an HTML/CSS change. Deploy was fused
to data-refresh.

**What shipped (commit `3f78f13`):** new **`.github/workflows/deploy.yml`** — a
push-triggered, **code-only** deploy path:
- `on: push` to `master` with `paths: ['web/**', '!web/data/**', '.github/workflows/deploy.yml']`
  + `workflow_dispatch`. Jobs: `build` (checkout + `upload-pages-artifact` path=web)
  → `deploy` (`deploy-pages`). **No Python, no download, no regen.**
- Enabler: `web/data/*.geojson` is **committed** (data-bot commits it each refresh),
  so a code deploy just re-uploads the existing `web/` tree — last-good data already
  on disk.
- `!web/data/**` exclusion = the bot's weekly data-only commit does NOT double-deploy
  (its own refresh run already deployed it). Any code file DOES trigger.
- Shared `concurrency: refresh-map-data` (`cancel-in-progress:false`) with
  `refresh.yml` → code deploy queues behind an in-flight refresh, never races on Pages.
- Action SHAs pinned identically to `refresh.yml` (checkout v7, upload-pages v5,
  deploy-pages v5).

**VERIFIED LIVE (not just reasoned):** the commit that added `deploy.yml` matched
its own path filter → triggered the **first real run** (`gh run 29966675803`):
**both jobs green, ~20 seconds.** Compared to recent `refresh.yml` runs (~5–12 min).
Negative case also confirmed: the follow-up **docs-only** push (`9d5e799`) did
**NOT** trigger deploy.yml — path filter works both ways. This is full
positive+negative verification of the trigger.

## 3. Technical Learnings
- **Two orthogonal triggers were fused:** "data changed" (weekly, needs
  download+regen) vs "code changed" (every push, needs neither). Splitting them is
  the whole win. `deploy.yml` (code, ~20s) + `refresh.yml` (data, ~min).
- **`rowsUpdatedAt` is a real, cheap change-signal** — Socrata `/api/views/{id}.json`
  exposes it per dataset (we already fetch that endpoint for year-alignment). Live
  check this session: **roads static 2+ months (2026-05-13)** while **permits + fire
  changed *today*** (2026-07-22). So a *global* "nothing changed → skip everything"
  almost never fires (daily-churning permits/fire); the value is *selective* skip of
  the slow static geo layers (roads = 62 MB + 900 s server-gen; zoning; boundaries).
- **Why selective regen is DEFERRED, not built:** skipping a download only helps if
  the raw file is available another way on a fresh CI VM (`data/raw/**` is gitignored,
  VM starts empty). That needs `actions/cache` for `data/raw/`, and the **weekly cron
  sits exactly on GitHub's 7-day cache-eviction boundary** → cache may evict right at
  the schedule (falls back to full download — safe, just no speedup). Real payoff,
  real fragility → separate project. Recorded in SPEC_deployment + TODO.
- **`deploy.yml` is the natural home for the S62 two-build split** — emitting the
  public-root + `/full/` copies is pure `web/` file-shaping (no data), so it belongs
  in the code path, factored as a shared step used by both workflows.
- **Key locations:** `.github/workflows/deploy.yml` (new), `.github/workflows/refresh.yml`
  (unchanged), `scripts/download_data.py` (15 SOURCES + `rowsUpdatedAt` unused today),
  `scripts/check_year_alignment.py` (already fetches view metadata).
