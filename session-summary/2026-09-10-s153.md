## 3. Technical Learnings

### `/output-style` DOES NOT EXIST AS A COMMAND ANY MORE — AND THAT IS ONLY HALF THE ANSWER

Two independent causes stacked, and each alone would have produced a different
error:

1. **The CLI folded it into `/config`.** The command table in the binary maps it
   literally: `"output-style":"config"` (alongside `keybindings:"config"`,
   `model:"config"`, `permissions:"config"`, …). So web-Claude pointing Peter at
   `/config` was **correct advice for a terminal session**.
2. **The web client does not render that section of `/config`.** Peter ran
   `/config` and got the claude.ai settings panel, which has no output-style
   picker at all.

⚠️ **The message he saw — "output styles aren't available for this session" —
is NOT in the CLI binary.** Grepped 2.1.268 for the phrase and for every nearby
variant (`output styles are…`, `…aren't available…`); the binary has
*Artifact watching is not available for this session* and several others, but
**nothing for output styles**. So the string comes from the **web front end**,
not the CLI. That is the evidence the cause is the client, not a CLI gate — and
it is why "restart the CLI" would not have fixed it.

**Unresolved and worth one measurement if it recurs:** this session also runs in
**Auto Mode**, which supplies its own system-prompt variant, and the binary's
prompt-source key set includes `auto_mode` beside
`repl_main_thread:outputStyle:Concise` / `:Proactive` / `:Explanatory` /
`:Learning` / `:custom`. **I did not prove which of the two (web client vs Auto
Mode) is refusing.** The clean test is a plain interactive `claude` in a terminal
on this box — if `/config` shows the picker there, it is purely the web client.

### THE SETTINGS SURFACE, VERIFIED FROM THE BINARY

- **Key:** `outputStyle`, a top-level string in `settings.json`. Sits beside
  `model`, `theme`, `effortLevel`, `fastMode`, `language`, `alwaysThinkingEnabled`.
- **Built-ins:** `Concise`, `Proactive`, `Explanatory`, `Learning` — enumerated
  from the `repl_main_thread:outputStyle:<name>` prompt-source keys, not guessed.
  `Explanatory`'s own description string: *"Claude explains its implementation
  choices and codebase patterns"*.
- **Custom styles:** a `.md` file with `name`/`description` frontmatter in a
  user-level `output-styles/` directory; body becomes the appended prompt
  (`{name, description, prompt: …trim(), source}`). ⚠️ **`~/.claude/output-styles/`
  does not exist on this box** — no custom styles are installed. Plugins can also
  ship them (`outputStyles` in `plugin.json`), and the binary warns when
  *"Multiple plugins have forced output styles"*.
- ⚠️ **Applies to NEW sessions only.** Writing the key does not restyle the
  running session — this one kept its original prompt after the edit.

### ⚠️ THE SETTING IS WEAKER THAN THE PREFERENCE IT ENCODES

Peter's actual ask, verbatim, was *"i wanted it to be more direct right? lack of
claude-isms etc"* — he chose `Concise` after checking with web-Claude, over a
custom style. **`Concise` is a proxy for that, not a statement of it**, and it can
silently fail to apply (Auto Mode, a bridged session, a client that ignores it).
The memory `direct-tone-no-claude-isms.md` therefore records **the preference**
and says to honour it whether or not the style is active. **Don't read a live
`outputStyle` value as evidence the preference is being met, or its absence as
evidence it is not.**

### VERSION DRIFT IS NORMAL HERE AND WILL MISLEAD A VERSION QUESTION

`claude --version` reported **2.1.265** while `~/.local/share/claude/versions/`
already held **2.1.268**, installed **21:39 the same evening** (auto-update writes
the new binary; the running process keeps the old one until restart). Five
versions are on disk: 2.1.235, 2.1.263, 2.1.265, 2.1.267, 2.1.268. ⚠️ **So
"what version am I on" has two true answers**, and if you grep a binary to explain
something the *running* session is doing, grep the version it is actually running
— I grepped 2.1.268 while running 2.1.265, which was fine for these stable strings
but is not safe in general.

### METHOD NOTE — GREPPING THE BINARY

`grep -ao` over the 215 MB ARM binary is fast and is how every claim above was
checked. Two gotchas hit this session:
- **`ugrep` is what `grep` resolves to here**, and it rejected a pattern as
  *"exceeds complexity limits"* (`.\{0,200\}…` with alternation). Simplify the
  pattern rather than escaping harder.
- Strings are stored **UTF-16-ish in places** (`T h e   m o s t   r e c e n t`),
  so a plain ASCII grep misses some text entirely. A miss is **not** proof of
  absence — which matters, because the "not in the binary" finding above is load-
  bearing. It survives because the *ASCII* neighbours (other `…for this session`
  strings) were found in the same pass, so the encoding was not the reason.
- ⚠️ Do **not** `pkill -f` a pattern typed in the same command (S152's lesson,
  still true).
