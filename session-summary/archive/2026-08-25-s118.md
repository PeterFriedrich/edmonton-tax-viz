## 3. Technical Learnings

### A DEAD BRANCH, AGAIN — the S117 pattern repeated on session entry
Started this session on `docs/s117-handoff`, whose PR (#234) had already
merged before the session began. All the doc-update work for the Infill grid
was done there before checking — caught before committing (per
`check-pr-state-before-committing`), recovered with the standard cycle:
`git stash -u` → `git checkout master` → `git pull` → `git checkout -b
feat/infill-amenity-grid` → `git stash pop` → commit there. This is now the
**second consecutive session** opening on a branch whose PR merged
mid-previous-session — worth checking branch/PR state as the FIRST action of
a session, not just before each commit.

### GitHub's merge-button default is STICKY PER BROWSER, not per-repo-setting
`allow_squash_merge`/`allow_merge_commit`/`allow_rebase_merge` are all `true`
at the repo level (unchanged) — that was never the mechanism. The dropdown
on GitHub's PR merge button remembers whatever method was last clicked **in
that browser session** and pre-selects it next time, for ANY PR, with no
time limit observed (>1 hour here) and no dependency on other PRs' state.
Practical consequence: Peter needs to manually reselect "Create a merge
commit" each time he wants that method, since one squash click resets the
default going forward. **Before attributing a squash commit to "the decision
got reversed" or "I did it again,"** check `gh pr view <n> --json mergedBy`
— it's cheap and settles the question immediately.

### Reusing an existing grid file across two lenses needs no data-contract change if the new consumer wants no new columns
`value_grid.json` already carried `dist_lrt_m`/`dist_school_m` (shipped
2026-08-23 for Glass). Infill's highlight grid consumes the exact same
`gridData.cells` array with zero pipeline changes — the only work was UI
wiring (view-gating, a new render layer, blurb text). The moment a "nicer"
version was floated (cells inherit their parent hood's colour), it stopped
being free: that needs a hood-id per cell, which `export_value_grid.py`
doesn't emit today. **Worth checking whether a data file already has what a
new consumer needs before assuming a pipeline change is required** — here it
did, in the adjacent "just filter, don't render a new metric" option Peter
picked.
