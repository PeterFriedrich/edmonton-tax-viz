## 3. Technical Learnings

### ⚠️ THE SESSION'S THEME: the instrument's *presentation regime* invalidated a published number

`about:support` was asked for to identify a GPU. It did — and incidentally
revealed **`Target Frame Rate: 60`**, which broke arithmetic nobody had
questioned across three prior captures.

- rAF frame times **quantise to multiples of 1/refresh**. The old laptop is
  **vsync-capped at 60 Hz**; the newer machine reported **117–139 fps**, i.e.
  above 60. **They were never in the same presentation regime.**
- 36.6 fps is a **mix of 1- and 2-vsync frames** (~64% spilled to two intervals),
  not a 27.3 ms render. Bounding the true marginal cost gives roughly
  **3–36 ms** — I had offered **19.4 ms** as a point estimate and **withdrew it
  within the same session**.
- ⚠️ **The already-recorded 0.981 ms is smaller than that machine's own vsync
  quantum** (6.9–8.3 ms). It was never a measured render cost.
- **What survives, and this matters:** mean fps over ~900 frames *is* a sound
  **monotone proxy** for render cost **within one machine at a fixed viewport**,
  because sub-quantum changes shift how many frames spill. So the **ratios
  (10.3%, 42%) stand**; only the millisecond conversion falls.
- ⚠️ **The 3.7% run may ALSO have been clipped** — its 139 fps is within 5% of a
  plausible 144 Hz panel. An independent *second* reason that figure was
  meaningless.

**Rule, now `docs/PERFORMANCE.md` rule 7:** record the refresh ceiling beside
every fps figure; never convert fps to milliseconds across machines.

### ⚠️ A guard can pass and still be the wrong guard

S130's snippet gained a `< 400 px` viewport floor after the 264 px run. Peter's
551 px capture **cleared it** while still being ~30% short of what a 900 px
screen allows. **An absolute threshold could not express the question**, which is
*"tall relative to this display"*. #307 rewrote it against `screen.height`
(< 65%). ⚠️ **All four captures ever taken — 264, 428, 503, 551 — trip the new
check; none tripped the old one.** No fps figure this project holds was taken at
a full viewport.

### ⚠️ The sanitised WebGL string was RIGHT this time — which is not reassurance

It read `Intel(R) HD Graphics` and the part really **is** HD 4400. On the other
machine the same string read `Intel(R) HD Graphics` for an **Iris Xe**. So it is
unreliable in **both** directions and **cannot tell you which case you are in**.
Refusing to read it stays correct. Always read `about:support`.

### ⚠️ Neither capture controlled the BROWSER, only the machine

The old-laptop run had **Dark Reader, AdBlock and uBlock Origin** all enabled.
**Dark Reader can apply a page-level CSS filter** — a fill-rate cost that scales
with viewport pixels, i.e. *the exact variable under test*. The newer machine's
extension set was never recorded. A controlled re-run means **extensions off
(private window / clean profile) AND viewport tall**.

### The ttfb split may not be about this site at all

That profile carries `security.pki.mitm_canary_issuer` naming an **Aruba network
appliance** (TLS interception somewhere in its history), plus
`network.http.speculative-parallel-limit: 0`, `network.prefetch-next: false`,
`network.dns.disablePrefetch: true` — all suppressing Firefox's own speculative
connections. **Whether the two machines shared a network was never recorded.**
⚠️ Those prefs do **not** affect the site's idle grid prefetch — that is a JS
`fetch()`, not a link prefetch.

### Environment quirks (this box) — all still true, none re-tested this session
- ⚠️ **`pkill` in a chain returns 144 and aborts it.** Use `kill <pid>`.
- ⚠️ **No GPU (SwiftShader)** — saturates at ~0.9 fps at BOTH grid resolutions
  and once reported the finer grid as *faster*. This is why client captures exist.
- ⚠️ System `python` is 3.6.8 — use `.venv/bin/python`.
- ⚠️ `sleep N && <cmd>` chains are **blocked** by the harness.
- ⚠️ **Run verify scripts ALONE** on this 4-core box.
