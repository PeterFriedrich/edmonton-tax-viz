## 3. Technical Learnings

### `check_road_classes` — the shape, and the three decisions inside it

`scripts/vintage_report.py`, registered in `CHECKS`, mirroring
`check_zoning_bylaw`. Ran live end to end: **12 rows, `✅ Road classes — All 15
… both directions`**.

1. ⚠️ **The population is the PIPELINE's, not the feed's, and the `$where` is
   built FROM `load_roads.CENTERLINE_TYPE` / `RESPONSIBLE_PARTY`** rather than
   restating them. **Measured:** the unfiltered feed groups into **16** values;
   `Road` + `City of Edmonton` holds **15**. The extra is `null` — the 14,229
   Alley/Railway rows. An unfiltered query would report drift in codes
   `_classify` cannot reach, and would diverge silently the day a filter moves.
2. **A null class on a City road row is a SEPARATE `ACTION` line** from a new
   code — same consequence, different fix (upstream defect vs a `CLASS_GROUP`
   entry).
3. ⚠️ **An empty vocabulary is `UNKNOWN`, checked BEFORE the null count.** A
   renamed column yields one null group; a naive reading reports all 15 codes
   GONE *and* every city road unclassed — two alarms from a shape change.

⚠️ **A GONE code is reported but is NOT a defect by itself.** `Alley-Commercial`
is **2 rows**, so a low-count code vanishes on an ordinary reclassification. The
count is in the message so the reader can tell that from a rename.

**Writing the null test found a defect in the MESSAGE, not the test:** the
null-only path was inheriting the new-code and GONE guidance. The advice now
tracks which direction fired.

### ⚠️ A COUNT IN THE DOCS WAS OFF BY ONE, IN THREE PLACES

### THE FALLBACK DECISION — why `local` was never a neutral default

**Peter's question forced this and it is the session's most transferable
reasoning.** `_classify` defaulted an unmatched code to `"local"` under *"no
silent data drops"*.

⚠️ **`collector + local` ARE `road_m_total`** → `road_m_per_acre` →
`cost_roads_life_per_acre`. So the "conservative" default was the **CHARGED**
one. `Alley-Commercial` proved it: an `Alley-*` code must leave the metric
entirely (**function governs**), and the fallback billed 106 m of it as road.

⚠️ **The general shape: the safe default and the correct answer point OPPOSITE
ways depending on what the new code turns out to BE, and the fallback fires
before anyone knows.** So it now asserts neither.

`DEFAULT_GROUP = "unknown"` — in `GROUPS` (carried as `road_m_unknown`), out of
`METRIC_GROUPS` (never billed).

- ⚠️ **The manual step did not change and was never avoidable** — all three
  options (fail open / fail closed / hold) end in one hand-written
  `CLASS_GROUP` entry. What changed is that the pipeline stops guessing during
  the wait, which #380 caps at ~30 days.
- **Under-billing is the accepted cost** — a hood reads LOW until mapped, the
  direction a fiscal argument survives being wrong in.
- ⚠️ **The served schema does NOT move**: `join_and_calculate.ROAD_COLUMNS` is
  `["road_m_total"]` only. **67 columns, still 67.**
- **Verified on the real 62 MB feed:** `road_m_unknown` **0.0**,
  `road_m_total` **3,654.1 km**, 405 hoods — unchanged.

### ⚠️ FIXING ONE SILENT PATH NEARLY CREATED ANOTHER, DOWNSTREAM OF IT

`unknown` is **not** in `export_roads_web`'s `t` map, so left alone it becomes a
**NaN `t`** — and **both** `== "access"` and `== "arterial"` exclude a NaN
without a word. The length would have left the map with no warning anywhere,
while `road_m_unknown` correctly reported it.

It is excluded **explicitly and logged**, with a test on the log line, **because
`access_m` IS the metric** — an unmapped segment drawn in the access layer would
move that neighbourhood's **colour**.

### ⚠️ TWICE THIS SESSION A "VACUOUS GUARD" WAS THE MUTATION'S FAULT

**Both times the harness was wrong, not the test. A green mutation needs one
more question before it becomes a finding.**

1. **#380** — three mutations left everything green. `check_zoning_bylaw`
   carries **character-identical lines** (`new, gone = sorted(...)`,
   `if not upstream:`), so a whole-file `replace(..., 1)` mutated **that**
   function while I ran **my** tests. Scoping the splice to the target function
   turned all three red by name. **Tenth instance of
   `check-where-the-value-can-be-wrong`** — the value couldn't be wrong because
   I mutated the wrong file region.
2. **#381** — routing `unknown → access` in the `t` map left everything green.
   That mutation is **INERT**: the explicit exclusion runs **before** the map,
   so the dict entry is dead code. **Proven by disabling both together**, which
   reds the access-layer test by name.

⚠️ **A real gap hid beside the second one** and was fixed: nothing tested the
citywide `road_m_unknown` warning in `load_roads` (the `_classify` per-code
warning is a different one). Covered now in both directions.

### ⚠️ THE ISSUE CHANNEL REACHES PETER AND NOBODY ELSE

**Peter's question, and the answer is no.** No background process, no
notifications, no state between sessions. The digest files a GitHub issue;
GitHub emails **Peter**. A session sees it **only** by running the command.

⚠️ **The first draft of the `CLAUDE.md` line was WRONG and running it caught
it.** I wrote `gh issue list --state open --search "digest in:title"`. There are
**three** titles and only one contains the word:

| title | source |

| `<flag> Vintage & pin digest — <date>` | `vintage_report.py:660` |
| `⚠️ Big revenue delta — <hood>` | `check_revenue_deltas.py:450` |
| `⚠️ Revenue-delta guard could not read its baseline` | `check_revenue_deltas.py:401` |

The filter would have **silently missed both delta issues** — including the
third, which means the guard **could not check**, not that a value moved.
⚠️ **Both commands return the same single result today**, because #296 is the
only open issue — it would have looked correct indefinitely and failed the first
time it mattered. **A filter that matches everything present is not a filter
that works.** Shipped as the plain `gh issue list --state open`.
