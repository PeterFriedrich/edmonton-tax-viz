## 3. Technical Learnings

### ⚠️ THE SESSION'S THEME: "cheap to change later" was true of the data and false of the prose

Peter's question — *"would it really be harder to make adjustments to the data,
after adding it to public"* — had a **two-part** answer, and the second part is
the one that produced work.

- **Cheap, genuinely:** a rate is one value in `data/city_unit_costs.json`, two
  test assertions (`test_join_and_calculate.py` pins `50.0` and `4.635` against
  the real file), and the next refresh recomputes. No column rename, no
  frontend restructure.
- ⚠️ **NOT cheap, and unguarded until this session:** the blurbs state rates as
  **prose** — `"$1,285 per kilometre"`, `"$50 per metre per year"` — and nothing
  tied those literals to the JSON. Change a rate and you ship a correct map
  under a stale sentence.

`scripts/check_cost_copy.py` closes it. Design notes that matter:

- ⚠️ **The load-bearing row is a RELATIONSHIP, not a rate.** The
  lifecycle-vs-operating gap is written **in words in three separate places**
  ("about eleven times" — a blurb, the panel note, the methods pod). A rate
  change moves it without touching any single quoted figure, so no per-rate
  check can see it and **two of the three sentences would go stale silently.**
- **Claims take the whole parsed file** (`expect: lambda c: ...`), not a path +
  formatter. That is what allows a relationship claim at all. My first cut used
  path+fmt and I had to restructure it when the ratio row would not fit.
- **Verified by FALSIFICATION, not by passing** — mutated the rates, confirmed
  it fails naming the exact expected string. (The standing lesson: an assertion
  placed where the value cannot be wrong passes under the bug.)
- **The two-bases test derives its expected ratio from the rates** rather than
  hardcoding 10.79 — otherwise the very edit we want to keep cheap would red
  the build.

### ⚠️ A test failure that was a real mobile fact, and a pre-existing flake underneath it

`verify-peek.js` failed 6 checks on the **full** build, deterministically
(4/4 runs), while master passed. Chasing it properly took most of the session's
debugging and found **two separate things**:

1. **A real measurement.** The Services cost panel grew **349 → 386 px** on a
   390×844 phone (top edge **487 → 450**) when the lifecycle row landed — so
   **37 px more map now sits under the bottom sheet.** The harness taps at
   y=464, which fell into exactly that newly-covered band.
2. **A latent flake that was always there.** `verify-peek` scanned tap targets
   in the **Money** view — against **extruded prisms at 52° pitch, panel
   closed** — then reused those screen coordinates in **Services**, where only a
   **flat** layer is pickable and the panel may be open. A prism's screen
   footprint sits well above its ground footprint, so whether the tap landed
   depended on which hood the Money scan happened to find first. **Master fails
   ~1 run in 5 on this alone** (measured: 1 failure in 5 runs).

Fix: the services block **re-derives its target in the view under test**.
Confirmed the fix on master too, so it removes the pre-existing flake.

⚠️ **The debugging lesson:** identical target hoods with different outcomes is
what proved it was mine and not the flake. Two probes that looked decisive were
**not** — an arbitrary probe coordinate returned `picked: null` on *both*
builds, and a direct `openTemporal()` call succeeded on *both*. Only replicating
the harness's own target scan and dumping `elementFromPoint` at the tap point
found it (`BUTTON#hoodmode-btn` on branch vs `CANVAS` on master).

⚠️ **Also: a stale-inode artifact cost a false red.** I `rm -rf`'d and rebuilt
`/tmp/site` **while an `http.server` was serving it**; four suites then reported
`EXIT=1` with **zero `FAIL` lines**. Restarting the server on a fresh port made
them all green. **If exit code and FAIL count disagree, suspect the server
before the code.**

### ⚠️ The `pub` tag: hiding the row is not the invariant

Public/full gating is a **`pub: true` tag on the service itself**, not scattered
`|| !FULL_BUILD` at each use site — row visibility, the colour radio and the
default checked set all read one tag, so a row cannot be published in one place
and hidden in another.

⚠️ **`state.services[k]` must also be cleared.** An unchecked-but-present
service is still reachable through the **colour radio** and still contributes a
**tooltip row** — clearing state is what actually keeps the number off the
public root.

### The legend/`primaryRow` trap held (and was designed for)

The services legend is an if/else chain whose `else` **prints the ROAD legend**,
and `primaryRow` falls to `|| []` → `"no X data"`. Both were added for
`roadslife` up front, and `verify-services-public.js` asserts the legend is **not
the road fallback by name**. This is the trap the bike lens shipped into.

### What the release plan already anticipated

The 2026-07-28 lock **wrote this session's rule in advance**: the three
full-only lenses return **one per release**, each reviewed against the release
copy. Services is the **first exercise**; Uses and Ratio follow the same path
separately. Worth doing the per-control tag properly because it is now the
template.

### ⚠️ OPEN AND UNRESOLVED — the two non-capital road figures disagree 2.6×

| figure | derivation | value |
|---|---|---|
| lifecycle O&M half | $600,000/km ÷ 50 yr | **$12/m/yr** |
| operating maintenance | Taproot/City staff, $1,285/km/yr + $3,350 snow | **$4.635/m/yr** |

Both claim to be **annual non-capital spend on neighbourhood roads**. Neither
has been traced to what it actually covers. The operating blurb now says
outright it is **the low end of a range**. This is a live caveat on a **public**
layer.

**A 7-question research prompt was written and given to Peter to run through
Claude web.** It is in the conversation, not saved to a file. The two questions
that would change the most:
1. What Edmonton's $600k/km "operate and maintain" actually includes (snow?
   lighting? sweeping, signs, signals?) vs the narrower $1,285/km "maintenance".
2. ⚠️ **Is there a better source class entirely** — the **Neighbourhood Renewal
   Program**'s actual per-neighbourhood spend. A uniform per-km rate cannot tell
   a 1960s neighbourhood from a 2015 one, which is precisely the distinction a
   revenue-vs-cost map exists to show. **That would be a real rework** (the
   metric stops being `metres × rate`), though the row/legend/panel machinery
   survives it.

⚠️ **Memory says Claude web invents file names and open questions** (4 false
claims on 2026-07-29). The prompt has explicit guardrails — cite a URL for every
figure, name the provenance class, say "could not verify this exists" rather
than naming a plausible-sounding report. **Grep before applying anything it
returns.**
