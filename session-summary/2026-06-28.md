**Revenue methodology — RESOLVED (`a736181`, `872ecb8`); see `docs/SPEC_revenue.md`:**
- Web research finding: assessed-value/acre is the **common convention** (Urban3
  = taxable assessed value/acre; Strong Towns how-to uses assessed value, not
  mill rates). So a rename alone would be legitimate.
- **Deciding insight:** applying a *uniform* rate just rescales the map (identical
  shape). The map only changes if **rates differ by class**. Edmonton's do
  (non-res ~3.2× residential), so the revenue phase IS worth doing — to capture
  the **class differential**, which re-ranks neighbourhoods.
- **DECIDED:** build the real revenue computation AND keep both metrics (value +
  revenue) as a web toggle. **Municipal-only** tax (City fiscal framing; education
  levy is provincial → excluded). **Exempt treatment:** denominator is the
  neighbourhood *boundary polygon area* (NOT summed parcel area), so "exclude
  exempt from denominator" isn't possible without parcel data we lack → use
  **$0-in-numerator, full boundary area**, and FLAG exempt-heavy neighbourhoods
  (downtown gov / Legislature will legitimately read low). **Year = 2025**
  (see below).

## 4. Technical Learnings

**Assessment dataset year is METADATA-ONLY (important):**
- The assessment CSV (`q7d6-ambg`, "Current Calendar Year") is a **live weekly
  feed** with **no year column in the rows**. The year lives only in Socrata
  metadata: `https://data.edmonton.ca/api/views/q7d6-ambg.json` →
  `custom_fields["Time Frame"]["Period of Coverage"]` (and the description:
  "effective 2025-01-01 to 2025-12-31").
- Our local snapshot (`data/raw/Property_Assessment_Data__Current_Calendar_Year_.csv`,
  downloaded 2026-05-16, 439,769 rows) is **2025** data. Recorded in DATA.md.
- A future re-download can roll the year → must re-check metadata and keep mill
  rates aligned. The revenue automation should auto-detect year from this metadata.

**Mill-rate dataset `pwis-wc4c` shape:**
- Columns: `tax_year`, `tax_rate_type` (Municipal / Education / Education
  Requisition Allowance), `assessment_class`, `amount_per_1_000_of_assessed_value`,
  `amount_per_dollar_of_assessed_value`.
- Query endpoint used: `https://data.edmonton.ca/resource/pwis-wc4c.json?$where=tax_year=2025`
- Quirks: class names use spaces ("Non Residential"); some historical years use
  hyphenated "Non-Residential". Rate-type label changed: 2014–2018 = "Municipal
  Tax Rate", 2019+ = "Municipal". 2025 dropped a separate Farmland class.
- Join key for our pipeline = the assessment **`Tax Class`** field (clean 4-value:
  Residential / Non Residential / Other Residential / Farmland) — cleaner than
  `Assessment Class 1` (which has COMMERCIAL / MA DERELICT RESIDENTIAL / etc.).

**Curl works in this environment** (the sandbox allowed `curl` to data.edmonton.ca).
WebSearch was used for methodology + rate research. WebFetch worked for
strongtowns.org but 403'd on the Strong Towns Action Lab (actionlab subdomain).

**Key file locations:**
- `main.py` — pipeline entrypoint; constants `ASSESSMENT_CSV`, `BOUNDARIES_GEOJSON`,
  `PNG_OUT`, `GEOJSON_OUT`, `SETBACK_M=45.0`, `SIMPLIFY_TOLERANCE_M=10.0`.
- `src/join_and_calculate.py` — `join_and_calculate()` (computes `value_per_acre`,
  line ~49) + `export_geojson(result, output_path, crs, setback_m, simplify_tolerance_m)`

**Revenue computation formula (from SPEC_revenue.md):**
```
levy = Σ_class  assessed_value × (class_% / 100) × (municipal_mill_rate[class] / 1000)
revenue_per_acre = Σ levy by neighbourhood / area_acres
```
