## 3. Technical Learnings

- **A PR branch can receive a push AFTER Peter has already merged it.** The
  merge only captures what existed on the branch at merge time; a later push
  to that same branch name lands on an orphaned ref, not on master. Symptom:
  `git log --all --oneline --graph` shows the later commit as a sibling of the
  merge commit, not an ancestor. This is the same failure mode flagged before
  (memory: "Check PR state before committing" / "Verify commits reached
  master") but manifesting mid-single-PR rather than across a whole branch —
  **check PR state before EVERY push to a branch you already opened a PR on,
  not just once at the start.**
- **`nbconvert --execute` needs a registered Jupyter kernelspec, which
  `ipykernel` provides as installed package data** (`<env>/share/jupyter/
  kernels/python3/kernel.json`, pointing `argv` at `python -m
  ipykernel_launcher`) — no `jupyter kernelspec install` step needed, just
  `pip install ipykernel`. Nothing in `nbconvert`'s or `nbclient`'s own
  dependency chain pulls this in (`pip show nbconvert`/`nbclient` — neither
  lists `ipykernel`), so a requirements file built by tracing `import`
  statements alone would miss it. Confirmed by testing in an **isolated**
  venv with **only** the proposed `requirements-ci.txt` pins — the system
  `python3` here is 3.6.8 (too old for the pipeline's other pins), so the
  isolated test used `/usr/bin/python3.12 -m venv` explicitly.
- **`build_site.py` needs zero code changes to publish `web/verified/`** — it
  already does `shutil.copytree(src, out)` for the whole `web/` tree at the
  public root; anything placed under `web/` rides along for free. `/full/`
  only needs a physical copy if something *inside it* links there via a
  relative path (which nothing does here — the About-panel link is a
  hardcoded absolute production URL).
- **`deploy.yml`'s path-filter semantics**: a single push touching both an
  included path (`web/index.html`) and a newly-excluded one
  (`web/verified/01_money_lens.html`) still fires the workflow — exclusion
  only suppresses the trigger when *nothing else* in the push matches an
  included pattern. This is what let PR #166's merge commit both add the
  exclusion **and** ship the first `web/verified/` files in the same push
  without a chicken-and-egg gap.
- **`verify-about.js`'s "link resolves" check hits production, not the test
  target** (`page.request.get(l.href, ...)` where `l.href` is each link's raw
  absolute `href` attribute) — this is why *any* new About-panel link pointing
  at a not-yet-merged doc will 404 in a pre-merge local run. Not a bug to
  chase; it's inherent to testing absolute external links locally.
