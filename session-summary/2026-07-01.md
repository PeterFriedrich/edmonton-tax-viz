- `fixa-tstc` has a `url` column whose PATH encodes the official bylaw section per zone:
  `…/part-2-…/residential-zones/…`, `…/industrial-zones/…`,

  category itself** — the bylaw groups are mixed. Clearest example: the

  level (as the handoff always said); `url` just catches dict errors.
- The `url` correctly resolves the handoff's `A*`-prefix trap: `AED`→`downtown-special-area`,
  `ALA`/`AUVC`→`ambleside-special-area` (NOT river valley). Good independent confirmation.

## 4. Technical Learnings

**The sqrt decision is the key intellectual result — and it's counter-intuitive:**
- Prior handoffs + FINDINGS §6 *predicted* the set-aside-excluded taxable core would
  be ≈ log-normal → use log. **The data said the opposite.** Excluding set-aside
  makes log-skew WORSE (−4.19), because `is_set_aside` at 0.90 only removes the
  ≥0.90 hoods while the mixed 0.55–0.90 band (kept on-scale BY DESIGN — that
  underdeveloped-but-developed land is the fiscal story) still holds near-zero-revenue
  land that dominates the left log-tail. So a single log scale over-corrects; sqrt is
  the answer. **Don't "fix" this by lowering the 0.90 threshold — the threshold is
  correct; the transform choice is what changes.**
- The skew estimator matters: FINDINGS §3 used the **biased** population skew (not
  pandas `.skew()` which is bias-corrected). `scripts/investigate_skew.py`
  `biased_skew()` reproduces §3 exactly (revenue 5.83 / −2.16). scipy is NOT installed
  in the `edmonton-tax` env — the script uses numpy only.

**load_zoning design choices that shouldn't be re-litigated:**
- Denominator is total *zoned* area per hood, not boundary `area_acres` — deliberate
  (robust to zoning/boundary edge gaps; fractions sum to 1).
- `DC`/`DC1`/`DC2` → `dev` (conservative default, won't wrongly hide land). Named
  natural special-area codes (`NSRVES`, `A7` Hawrelak…) get their OWN explicit entry.
- `BP` (Blatchford Parks) → `never`; the 0.90 threshold means a few park polygons in
  a developing neighbourhood won't flip the whole hood.

**The residential-lens blocker (for the TODO):** `load_zoning` lumps residential +
commercial + industrial + mixed all into `dev`, and `join_and_calculate` exports only
the 3 set-aside cols — the per-category `frac_*` are computed then dropped. So the
"residential-only" view is genuinely unbuilt AND needs a pipeline extension first (see
TODO). `is_residential` (a display filter) must stay orthogonal to `is_set_aside`.

**Height was ALREADY linear** (`getElevation: f => f.properties[cfg.key]`, fixed
`elevationScale`, locked "honesty choice"). A claude.ai design convo framed 3 "lenses"
(sqrt / linear-height / residential-only); verified only sqrt-colour was new work,
linear-height is the existing default, residential-only is unbuilt. The current single
view already fuses sqrt-colour + linear-height.

## 4. Technical Learnings

**The dry-run-before-CI discipline paid off immediately.** Running the exact workflow
command chain locally (`download_data.py` → `main.py --skip-png` → `generate_status.py`)
surfaced the `DESIGNATED IND PROPERTIES` KeyError that would otherwise have broken
*every weekly CI run* silently. **Always dry-run the CI chain locally before trusting
a scheduled Action.** The no-silent-drop guard in `apply_tax_rates` is what made it a
loud failure instead of a wrong map.

**DIP mapping (don't re-litigate):** `DESIGNATED IND PROPERTIES` → `Non Residential`.
Designated Industrial Property (provincially-assessed plants/linear/machinery) is
non-residential for the municipal levy (the only rate we apply); the parcel's own
`Tax Class` field confirms it. 1 parcel — negligible impact, but the guard forces us
to classify it explicitly.

last changed (gated on `_geojson_sha256`), `last_checked` = every run (heartbeat that

## 4. Technical Learnings

**The audit's method finding — spatial containment resolves name mismatches
decisively.** The assessment CSV has Latitude/Longitude; `gpd.sjoin(points,
boundaries, predicate="within")` turned all three "known-unresolved" unmatched
names into confirmed mappings in one query. DATA.md Name Matching now says: any
NEW unmatched name is drift — use this test.

**Partial name match is worse than no match.** HVTC rendered *wrong* (not
missing) because a small direct-name slice existed alongside the big "...AREA"
slice. "Unmatched = visibly absent" was the wrong mental model; the audit brief's
framing (silent plausible-wrong > loud missing) is what surfaced it.

**Fable-vs-brief design decision (why DATA_INTEGRITY.md is a checklist):**
open-ended "reason about risk" briefs suit strong models doing discovery;
for a fast executor, pre-rank the risks (done once, with repo history) and cast
each as a verifiable claim. The §4 completeness pass keeps the discovery escape
hatch. (The brief's first run was actually executed by Opus in-session.)
