#### B. The police-driver crime-data probe (PR #232)

Peter asked to check a relayed claim: *"Official Edmonton crime data is
accessible programmatically through the Community Safety Data Portal...

**The claim is wrong, corrected for the record.** OGC API - Records is a

FeatureServer**.

**What's actually there, confirmed live via WebFetch against the Esri REST
API JSON endpoints (not the JS-rendered dashboard, which WebFetch can't
read):**
- `EPS_OCC_30DAY` — rolling 30-day window only, no use as an annual driver.

  onward**, ~293K incidents, 2,000 records/query (needs pagination). Fields:
  `Reported_Date`, `Occurrence_Category`, `Occurrence_Group`,
  `Occurrence_Type_Group`, `Intersection`. **No neighbourhood/ward field** —
  would need a point-in-polygon join, same pattern this project already uses
  for schools/LRT.
- Endpoint: `https://services9.arcgis.com/pkzvt2xlZJnPgk1Z/arcgis/rest/services/Historic_Occurrences_CSDP/FeatureServer/0`

**Why this doesn't unblock police allocation anyway:** the dataset's own
description says locations are anonymized to the nearest intersection

against the exact per-area comparison a police-cost driver would need —

## 3. Technical Learnings

### ⚠️ A DEAD BRANCH CANNOT BE COMMITTED TO — even mid-session, even for a
### one-line fix
`feat/amenity-distance` (PR #230) merged **while the police-research docs
edits were sitting uncommitted on it, mid-session.** Standard recovery each
time: `git stash -u` → `git checkout master` → `git pull` → `git checkout -b
<new-branch>` → `git stash pop` → commit there. Did this **three times this
session** (once for the CI fix, once for the police docs, once for the
break-even decisions) because each new branch's own PR also got merged
within minutes of opening. **This is the `check-pr-state-before-committing`
memory pattern operating at a tighter cadence than usual — check before
every commit, not just every session.**

### ⚠️ SQUASH VS MERGE COMMIT IS A REAL WORKFLOW TRADEOFF, NOT JUST STYLE
Ran `gh pr merge --squash` on #231/#232 out of habit. Squash produces a
**new commit SHA** on master — the original branch-tip SHA that
`check-pr-state-before-committing`/`verify-commits-reached-master`'s
`merge-base --is-ancestor` check expects **never lands on master**. Peter's
own history (PR #226–230) is exclusively merge commits via the GitHub UI
button. Explained the three GitHub merge options and their tradeoffs (merge
commit: full history, noisier log, harder single-command revert; squash:
clean linear log, breaks SHA-based checks; rebase: linear + full history,
same SHA-rewrite caveat as squash). **Peter's call: merge commits, for now.**
Saved as `pr-merge-method-merge-commit.md`.

### THE FAST-FAILURE DURATION TELL
A CI run failing in **~1 minute** against a normal **8–20 minute** successful
run is itself diagnostic — it means the failure is in setup/dependency
resolution (here: `pytest` collection erroring on `ModuleNotFoundError`
before any pipeline code runs), not in the data pipeline itself. Worth
checking run *duration* before diving into logs.

### `requirements.txt` vs `requirements-ci.txt` — TWO FILES, MUST STAY IN LOCKSTEP
`requirements.txt` is the full local-env freeze (includes JupyterLab, used
for local exploration only). `requirements-ci.txt` is deliberately slim
(only what `main.py` + tests need) so the GitHub Action installs fast. **Any
new `src/` import from a package not already in the slim file breaks CI
silently until the guard step fails** — this is exactly what happened here.
The slim file's own header comment already says to bump it in lockstep; that
comment did not get followed in #230. No new guard added this session — the
existing test-collection-before-regenerate gate is what caught it (correctly
blocked a downstream bad-data commit from happening), it just wasn't
followed at merge time.
