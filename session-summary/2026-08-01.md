**⚠️ SPLIT THE GESTURE FROM THE CONTENT WHEN VERIFYING — 7 minutes vs 40

## C3. Technical Learnings

**⚠️ THE 45.1% CHROME FIGURE WAS INFLATED AND HAD DRIVEN THE MOBILE BACKLOG FOR
SIX SESSIONS.** The 2026-07-27 method summed visible chrome rects *ignoring
mutual overlap*, but the chrome **nests** — `#controls` contains
`#views`/`#toggle`/`#optpanel`/`#layers`, `#botleft` contains `#legend` — so
containers were counted two and three times. Counting each pixel once:

| state | 390×844 | 1440×900 |
|---|---|---|
| default | sum 37.9% · **union 27.9%** | sum 31.6% · **union 20.9%** |
| **Options UNFOLDED** | sum 94.9% · **union 54.3%** | 20.9% |
| default + peek card | sum 53.2% · **union 34.5%** | n/a |

**The default phone render is NOT the problem** (~7-point gap to desktop, not
~18). **The problem is one state the aggregate averaged away: the unfolded
Options pod at 54.3%.** If a bottom sheet is ever built, scope it to that.
⚠️ **Generalisable: an overlap-blind sum over a nested DOM is not a coverage
metric.** Quote the union and name the state.

**⚠️ THE OBVIOUS ZONING SOURCE WAS THE WRONG ONE, and only measurement showed
it.** `dkk9-cj3x`'s per-property `zoning` joins to the roll cleanly (1:1, no
dupes, every tax class matched) — and is **null for 35.7% of properties, 16.0%
of citywide revenue, 42% of DOWNTOWN's**, because condo units carry no zoning.
"Top 3 zones" on that field showed **`unzoned` as Downtown's largest entry**.
Point-in-polygon against `zoning.geojson` filled **11,022/11,022** of Downtown's
and cut citywide unplaced to **0.002%**. ⚠️ **The deciding argument was
CONSISTENCY, not coverage**: those are the same polygons the Uses lens colours
by area, so the two lenses are one map read two ways and `ZONE_CATEGORY` is
reused rather than re-expressed.

**⚠️ A LOCAL `python main.py` ROLLS THE PUBLISHED DATA BACKWARD.** `data/raw/` on
this box is **2026-07-06**; the committed geojson comes from the **2026-07-27**
auto-refresh, which downloads fresh data every run. A regeneration meant only to
ADD columns changed **1,896 pre-existing values** across 406 features. **Nothing
was committed.** Now `RUNBOOK.md` §3b. **Consequence for phase 2: the new
columns are ABSENT from the served geojson until `refresh.yml` next runs, so the
UI must degrade cleanly without them.**

**TWO SILENT PANDAS/GEOPANDAS TRAPS, both of which produced confident wrong
numbers before being caught:**
- **`.str.split().str[0]` on an empty string yields `NaN`, not `""`.** An
  "unmatched code" filter written the obvious way swallowed every null-zoning row
  and reported **16.04%** of revenue sitting in three rare codes. The true figure
  is **0.003%**. I nearly reported the wrong one.
- **`gpd.sjoin` where BOTH frames carry the same column name** suffixes them to
  `_left`/`_right`, so the later lookup `KeyError`s — or worse, silently reads
  the wrong side. Drop the left one before joining.

**A TEST CAUGHT A CRASH THE REAL DATA CANNOT REACH.** `%,.0f` is invalid in
`%`-style logging (`,` is format-spec syntax, not `%`-syntax). It sits on the
no-coordinates path, which is **empty today at 100% coordinate coverage** — so
the pipeline ran green and the bug would have surfaced only when the data
changed.

**`join_and_calculate` RETURNS `joined[out_cols]` — AN EXPLICIT ALLOW-LIST.**
Adding a column to `SLIM_COLUMNS` is **not enough**; it is dropped upstream
unless also added to `out_cols` (new `REVENUE_READOUT_COLUMNS`). Cost one full
pipeline run to spot: the export gained `total_revenue` but silently not the
other eleven.

**PAYLOAD: ROUND EXPORTED FRACTIONS.** Full float repr is ~19 chars for a value
needing 4. The 12 new columns cost **+33 kB gzipped unrounded vs +4 kB at 1e-6**
— a 7× reduction for precision 4 orders below anything the readout can show.
